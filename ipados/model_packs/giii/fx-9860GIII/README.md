# fx-9860GIII model package (TAG: PKG9860)

A **data-only** CasioEmuMsvc board-model pack for the Casio fx-9860GIII
(aka Graph 35+E II). It declares the board geometry, key matrix and the
architecture descriptor; it does **not** contain an architecture core and
**does not claim that any operating system boots**.

Status: **OS IMAGES DECODED; bootcode + boot demo still PENDING.** The genuine
3.71 OS image is decoded and wired as `flash_path`; no bootcode exists and no
boot has been demonstrated (see `../PKG9860_REPORT.md`). Run
`python3 ../tools/verify_package.py` for the authoritative status.

## 1. Layout

| File | Role | Origin |
| --- | --- | --- |
| `config.json` | Model config; `board_path` + GIII `extra` descriptor keys | Authored here, generated by `../tools/generate_layout.py` |
| `board.svg` | Screen slot + key hit regions (`data-ki`/`data-ko` single-bit masks) | Generated from the public gint key matrix; **schematic**, not traced from hardware |
| `keymap.json` | Matrix codes (`kiko = (row<<4)\|col`) + SDL suggestions | Derived from `include/gint/keycodes.h` |
| `interface.png` | Loadable skin placeholder (640x1180) | Generated by `../tools/generate_placeholder_skin.py`; **watermarked schematic, not a real product image** |
| `os.bin` | **Decoded primary GIII OS 3.71 image** (RCDATA 3070) | Raw-DEFLATE decode of the genuine blob; wired as `flash_path` |
| `os_3071.bin` | Decoded alternate GIII OS 3.71 image (RCDATA 3071) | Same method; kept as variant, not wired |
| `os_payload/*.bin` | The four original **encoded** resources (provenance) | Copied byte-for-byte from OSEXTRACT `OS_IMAGES/`; 3072/3069 fail decoding |
| `../os_manifest.json` | Real paths, sizes, SHA256, decode status, caveats, rename plan | Source of truth for verification |
| `rom.bin` | Proven bootcode | **PENDING — does not exist**; `rom_path` stays empty |

`config.bin` is intentionally **not** shipped: the host regenerates it from
`config.json` on first load, so there is no stale binary cache to mask edits.

## 2. ISA caveat — read this first

The tag `PKG9860` (and the companion `SH3PLUGIN` work item) uses "SH3" as a
**historical label**. Public technical evidence says the fx-9860GIII is an
**SH-4A / SH7305-class** machine, **not SH-3**:

- G3Emu, a public fx-9860GIII emulator, is built around `SH4ACPUCore` plus
  `SH7305MPU` and models the Toshiba **T6K11** LCD controller
  (<https://github.com/summerx73/G3Emu>).
- gint lists `HWCALC_G35PE2` (Graph 35+E II = fx-9860GIII) among its SH4-family
  targets and selects T6K11 **version 2** for it
  (<https://git.planet-casio.com/Lephenixnoir/gint>).
- A community hardware write-up identifies the 2011+ "GII-2"/GIII-class SH7305
  as an SH-4A (<https://media.taricorp.net/prizm/simon_chm/fx9860GII_2.htm>).
- True SH-3 is the older fx-9860G / fx-9860GII (SH7337 / SH7355).
- The published deep-research deliverable `/mnt/code/research/SH3RESEARCH.md`
  reaches the same conclusion (§1.2). Full source excerpts and URLs are in
  `../docs/HARDWARE_EVIDENCE.md`.

Consequence: `arch_architecture` is `sh4a`, and `arch_provider` points at the
current fx-9860GIII provider id (`sh3.giii.skeleton`). The provider id is an
**opaque host dispatch string, not an ISA claim**; it is the ID actually
registered by the sibling SH3PLUGIN skeleton, so keeping it preserves real
dispatch. The "sh3" token is a legacy project tag that conflicts with the
verified SH-4A class. We did **not** invent an ISA-correct id that no provider
registers. The mismatch is recorded explicitly (with a rename plan) in
`../os_manifest.json` → `provider_naming`, and the verifier checks that record;
when a real core registers e.g. `giii.sh4a.core`, changing only `arch_provider`
fixes it with no host code change.

## 3. Hardware facts used by this pack

| Property | Value | Source |
| --- | --- | --- |
| LCD dimensions | 128 x 64 dots | gint `display-fx.h`: `DWIDTH 128`, `DHEIGHT 64` |
| Pixel format | 1 bit per pixel, monochrome; VRAM = 1024 bytes | gint `display-fx.h` (1024-byte VRAM); G3Emu `T6K11.h` ("128*64/8 byte array") |
| LCD controller | Toshiba **T6K11**, **version 2** on Graph 35+E II | gint `src/t6k11/t6k11.c` (`HWCALC_G35PE2` -> v2); G3Emu `T6K11.cpp` |
| CPU clock (default) | **58 MHz** (gint Ftune F1 for G-III / Graph 35+E II) | gint `include/gint/clock.h` |
| Key scan | SH7305 KEYSC at `0xa44b0000`, 12 registers x 8 bits | gint `src/keysc/keysc.c`; G3Emu `G3Keybd.cpp` |
| AC/ON | matrix code `0x07` = row 0, col 7 (own row to avoid ghosting) | gint `keycodes.h` (`KEY_ACON=0x07`) |

### Descriptor values (`config.json` → `extra`)

| Key | Value | Why |
| --- | --- | --- |
| `arch_provider` | `sh3.giii.skeleton` | Real ID registered by SH3PLUGIN; see caveat above |
| `arch_architecture` | `sh4a` | Informational; actual ISA class |
| `arch_fb_width` / `arch_fb_height` | `128` / `64` | Matches the real 1bpp LCD geometry |
| `arch_cycles_per_second` | `58000000` | Host cycle budget = gint's documented G-III default Iphi (58 MHz) |
| `arch_cabi_prefix` | `giii_` | Namespace for optional C ABI counters |
| `arch_power_key_row` / `arch_power_key_col` | `0` / `7` | AC/ON matrix contact, `kiko 0x07` |

Note on the cycle budget: gint also documents overclock levels F4 (118 MHz)
and F5 (235 MHz), and G3Emu's initial CPG registers correspond to about
118 MHz. We deliberately choose the **stock 58 MHz default** for reproducibility;
raising it later is a one-line config change, not a host change.

## 4. Keymap

`keymap.json` lists 50 keys with gint matrix codes. `board.svg` encodes each as
`data-ki = 1<<col`, `data-ko = 1<<row`, which the host converts to
`kiko = (row<<4)|col`. `config.json.buttons` carries the same codes in the same
order. The verification script checks all three representations agree.

SDL names are convenience bindings only; the matrix code is authoritative.

## 5. OS payload provenance — READ THE CAVEAT

Official installer (public Casio support site, verified SHA256):

- `20_2_fx-9860g3_G35_series_update_371_2b.zip`, OS 3.71,
  SHA256 `3a1a56d70968f14f4c50b98ea52051c5896fb02d0a5a004844523e6fe76f4322`
- URL: <https://www.casio.com/content/dam/casio/global/edu-casio-com/download/files/20_2_fx-9860g3_G35_series_update_371_2b.zip>

OSEXTRACT extracted the genuine PE RCDATA resources from the official updater
DLL. Those blobs were copied byte-for-byte into `os_payload/` and their SHA256
values re-verified locally. Two of them subsequently decoded cleanly with
**RFC1951 raw DEFLATE from byte 0, wbits=-15, plus an opaque 8-byte trailer**
(public CG100 prior art, `HOW_IT_WORKS.md` §1). Independent zlib decode and
marker checks confirm:

| Decoded image | From | Size | SHA256 | Markers |
| --- | --- | --- | --- | --- |
| `os.bin` (wired) | RCDATA 3070 | 3,866,622 | `fb6f3933f52ee3181f15940ea3c542b381631a31a6517a9582b8db20a506ce31` | `CASIOWIN` @0xfab6, `03.71.0000` @0x1001e |
| `os_3071.bin` | RCDATA 3071 | 3,866,621 | `6bf297fddb956456e98da54ce31d800165ab480aca3cba9b89d90b3fce8c97b9` | `CASIOWIN` @0xfab5, `03.71.0000` @0x1001d |

Encoded originals remain in `os_payload/` with hashes
`83505beb…` (3070), `6523102e…` (3071), `fca2f0da…` (3072),
`46d78520…` (aux 3069).

**CAVEAT (do not skip):** RCDATA 3072 and aux 3069 **still fail** to decode
(`invalid distance too far back`) and are kept only as raw encoded resources —
nothing was fabricated for them. The aux 3069 role is unproven; it is **not**
called bootcode. Per SH3RESEARCH §5, bootcode cannot come from installers.
`flash_path` is wired to the decoded primary image, but:

- `rom_path` stays **empty** — no proven bootcode file exists.
- The decoded image has **not been boot-tested**; the provider is a skeleton.
- A boot demonstration and a bootcode file remain explicit **PENDING** items.
- **No OS boot is claimed or demonstrated.**

## 6. Limitations / non-claims

- No SH-3/SH-4A instruction is executed by this package; it contains **no core**.
- The referenced provider (`sh3.giii.skeleton`) is currently a **skeleton** in
  SH3PLUGIN whose core refuses initialization. Launching this pack today will
  not run the GIII OS.
- The shipped `interface.png` is a schematic placeholder, not a real skin.
- No screenshot, boot animation, key response or framebuffer output is claimed.
- No exam-mode material was read, copied or used. No hardware was flashed.

## 7. Reproduce / verify

```sh
cd /mnt/code/worktrees/pkg-9860
python3 tools/import_decoded_os.py          # regenerate os.bin / os_3071.bin from genuine blobs
python3 tools/generate_layout.py --model-dir fx-9860GIII --flash-path os.bin
python3 tools/generate_placeholder_skin.py --out fx-9860GIII/interface.png

```

Do **not** set `--rom-path` until a proven bootcode file actually exists. The
verifier currently reports `0 FAIL / 3 PENDING` (bootcode, boot demonstration,
plus the manifest's documented outlier/provider-rename/skin items) — the
correct honest state: data, real hashes and the decoded image check out, but
no boot was ever demonstrated.
